ГЛАВА 2. ПРОЕКТИРОВАНИЕ И РЕАЛИЗАЦИЯ ИНФОРМАЦИОННО-ПОИСКОВОГО И ДИАЛОГОВОГО КОМПЛЕКСА
2.1. Обоснованный выбор стека технологий для реализации ассистента
Подсистему серверного приложения целесообразно реализовать на языке Python 3.12 ввиду наличия зрелой экосистемы библиотек машинного обучения и прикладного NLP, совместимой с используемыми компонентами оркестрации агента. В качестве каркаса HTTP API был выбран фреймворк FastAPI: он поддерживает асинхронный ввод‑вывод, декларативное описание контрактов запросов/ответов и автоматическую генерацию документации OpenAPI, что упрощает интеграцию с клиентским SPA и воспроизводимость сценариев тестирования. В качестве ASGI‑сервера применён Uvicorn как вычислительно типовое решение для развёртывания приложений FastAPI в контейнерной среде. Для валидации и сериализации данных используется Pydantic, что снижает риск несогласования схем API с фактической структурой полезной нагрузки и упрощает контроль типов для входящих параметров загрузки и формата диалогового запроса.

Слой оркестрации диалогового агента базируется на связке LangGraph и компонентов экосистемы LangChain как на инструменте, позволяющем формально описывать граф состояния вычисления, переходы между узлами и подключение внешних инструментов как функций наблюдаемого исполнения. Данная инженерная схема согласуется с требованиями главы 1 по управляемости ветвлениями и с практической необходимостью интеграции в единый конвейер как RAG‑операций, так и условных переходов к веб‑поиску и узлам сервисного вызова. На уровне провайдеров генерации применена облачная модель семейства Google Gemini через официально поддерживаемую интеграцию языковых моделей, что обеспечивает воспроизводимость клиентских вызовов и возможность конфигурирования параметров генерации отдельно для маршрутизатора и для финального синтеза ответа.

Для векторной индексации локального корпуса выбрано хранилище Qdrant с HTTP‑интерфейсом, опирающееся на фиксируемую размерность векторов коллекции и метрики близости, согласуемые с конвейером семантического поиска. Для кодирования фрагментов документов и запросов применён локальный провайдер эмбеддингов Ollama, что поддерживает схему «внутреннее извлечение без принудительного обращения к внешнему эмбеддинг‑SaaS» при условии развёртывания службы модели эмбеддингов совместно с приложением и строгом согласовании размерности вектора с параметрами коллекции Qdrant. Для клиентской части применены React и TypeScript как основа SPA с явной статической моделью компонентов и снижением ошибок интеграции с контрактом API. Инструментарий сборки Vite представляет собой типовое решение для разработческого цикла и продакшн‑бандла статических ресурсов. Для описания интерфейсных стилей использован Tailwind CSS как технология утилитарной стилизации, обеспечивающая поддерживаемость макета и предсказуемость набора классов при разработке интерфейса чата и сопряжённых экранных элементов.

2.2. Архитектура клиент-серверного взаимодействия и проксирующие элементы конфигурации
Вычислительная топология системы строится по схеме «клиент — обратное проксирование — сервер приложений — подсистема агента — внешние сервисы». Пользовательский доступ к приложению осуществляется из веб‑браузера, выполняющего загрузку статических ресурсов интерфейса и формирующего HTTP‑запросы к интерфейсным ресурсам и к программному API. В конфигурации контейнерного развёртывания внешняя экспозиция веб‑клиента реализована службой Nginx; для унификации адресации к backend‑эндпоинтам применяется проксирующее правило на префикс /api/ с передачей запроса на сервер FastAPI без дублирования логики маршрутизации на клиенте. Таким образом, браузер обращается к API по относительному пути, а фактический перенаправляемый ресурс формируется на уровне прокси‑шлюза, что упрощает сопоставление путей между средой сборки и эксплуатации.

Разграничение функциональных сценариев на уровне HTTP реализовано раздельными маршрутами: ресурс синтеза ответа ассистента соответствует диалоговому режиму (представление естественно‑языкового запроса и получение текстового результата), а ресурс приёма файлов выполняет загрузку пользовательских документов с последующим запуском конвейера индексирования. Дополнительно предусмотрены ресурсы проверки состояния приложения («жизнеспособность» и «готовность зависимостей»), применимые для контроля восстановления после сбоев и для сценариев оркестрации контейнеров. Программное обеспечение FastAPI включает слой промежуточной обработки запросов, обеспечивающий трассируемость обращений (идентификатор запроса в заголовке), что относится к эксплуатационным требованиям наблюдаемости и не противоречит клиентско‑серверной модели, поскольку не изменяет семантику бизнес‑операций, а дополняет транспортный контур.

2.3. Модель состояния и граф управления диалогом на базе LangGraph
flowchart TB
  N0([начало]) --> N1[узел router]
  N1 -->|next_step=rag| N2[узел rag]
  N1 -->|next_step из набора: погода / вики / видео / калькулятор| N3[инструментальный узел]
  N1 -->|next_step=web_search| N4[узел rewrite]
  N1 -->|next_step=direct| N9[узел generator]

  N2 --> N5[узел grader]
  N5 -->|is_relevant=yes| N9
  N5 -->|is_relevant=no| N6[узел rewrite]

  N4 --> N7[узел search]
  N6 --> N7
  N7 --> N9

  N3 --> N9
  N9 --> N8[узел reflection]

  N8 -->|reflection_branch=retry| N9
  N8 -->|reflection_branch=done| N10([конец])

Совокупное состояние агента описывается типом «словарь с фиксированным набором полей» (AgentState, app/agent/state.py) с частичной обязательностью полей (total=False). Поле messages хранит список сообщений фреймворка LangChain и обновляется редуктором add_messages: новые сообщения добавляются к истории, а не подменяют её целиком. Поле next_step задаёт дискретную метку следующего этапа из допустимого перечня литералов (rag, weather, web_search, wikipedia, youtube, direct, calculator). Поле is_relevant принимает значения "yes" или "no" и используется условным переходом после оценки качества локального контекста. Поля reflection_branch ("retry" или "done") и reflection_retry_count задают политику пост‑генерационного контроля и ограничивают число повторов. Решение маршрутизатора может формироваться как структурированная схема RouteResponse (поля «следующий шаг», «краткое обоснование»); в состоянии графа фиксируется прежде всего выбранный переход next_step.

Граф собирается функцией build_graph() (app/agent/graph.py) как объект StateGraph с типом состояния AgentState. Точкой входа назначен узел router. Условное ветвление из router реализовано селектором state["next_step"]: при выборе локального поиска по коллекции переход выполняется в rag; при выборе сервисных сценариев — в соответствующий инструментальный узел; при выборе сетевого поиска «сразу по запросу пользователя» переход идёт в rewrite; при прямой генерации без инструментального шага — в generator. Для ветви rag зафиксирована последовательность rag → grader. Узел grader ветвит поток по значению is_relevant: при подтверждённой пригодности контекста переход выполняется в generator, при отклонении контекста — в rewrite. Для узлов погоды, энциклопедии, видеопоиска и калькулятора заданы прямые рёбра → generator. После rewrite всегда следует search, затем снова generator. Узел generator соединён с reflection. Из reflection при reflection_branch == "retry" выполняется возврат к generator (не более одной итерации согласно логике узла), при иных значениях поля — завершение графа (END).

Содержательно узел router либо принудительно направляет выполнение на видеопоиск при текстовых признаках явного намерения пользователя получить ролики, либо вызывает языковую модель маршрутизатора с требованием структурированного результата типа RouteResponse; при ошибке вызова выбирается запасной сценарий direct. Узел rag вызывает метод поиска локального корпуса и добавляет сообщение ассистента с контекстным префиксом, задаваемым константой RAG_CONTEXT_PREFIX. Узел grader при отсутствии текста локального контекста устанавливает отрицательную релевантность; при признаках успешного попадания индексированных фрагментов в ответе пропускает лексический фильтр и устанавливает положительную релевантность; иначе применяется функция быстрой лексической проверки из app/agent/grader.py. Узел rewrite формирует поисковую формулировку по шаблону переписывания и фиксирует её как текст последнего сообщения для узла search. Узел search считывает последнюю реплику как запрос поиска и создаёт сообщение с результатом внешнего веб‑извлечения (инструмент семейства DuckDuckGo) с повтором при сбоях согласно настройкам. Узел generator допускает возврат результата без вызова генеративной модели при заранее подготовленных ответах калькулятора и отдельном сценарии явного видеозапроса; в типовом режиме выполняется вызов модели ответа при сборке списка сообщений, при этом при is_relevant == "no" из контекста генерации исключаются локальные сообщения с префиксом RAG_CONTEXT_PREFIX, чтобы не использовать отбракованный извлечённый текст. Узел reflection запрашивает числовую оценку и текстовую обратную связь по черновику; при очень низкой оценке (как задано условиями в коде: меньше порога «удовлетворительности») допускается одна повторная генерация через добавление системной инструкции с замечаниями, иначе ветка завершается.

2.4. Пайплайн извлечения по локальному корпусу и лексическая проверка релевантности
Индексирование и семантический отбор строк реализуются в классе службы RAGService (app/services/rag_service.py). Документ при поступлении на индексирование разбивается на перекрывающиеся фрагменты сплиттером RecursiveCharacterTextSplitter с параметрами приложения («размер фрагмента», «перекрытие»), затем векторизуется эмбеддинг‑моделью через связку LangChain‑Ollama и записывается в коллекцию векторного хранилища Qdrant; при создании коллекции задаётся метрика сходства типа «косинусное расстояние» из перечисления Distance.

На этапе запроса метод query вычисляет подсказки hints_from_question: из текста вопроса извлекаются имена файлов с расширениями текстовых и учебных форматов из фиксированного набора, а также возможные упоминания источников после ключевых слов вроде «файл», «документ», «конспект». Базово используется глубина выдачи top_k, равная настройке rag_search_limit. При наличии подсказок увеличивается параметр расширенной выборки fetch_k с верхней границей 48 по правилу, заданному в коде. Выполняется два семантических поиска по хранилищу: по исходной формулировке вопроса с параметром k=fetch_k и, при наличии подсказок, дополнительный поиск по объединённой строке подсказок с отдельным допустимым k. Результаты удаляются от повторов с сохранением порядка в ранжировании сходства, затем выделяются фрагменты, чьи метаданные имени или пути согласованы с подсказками, и объединяются так, что согласованные кандидаты поднимаются в начало списка; итог усекается до top_k. Итоговая строка для диалогового контура формируется как последовательность блоков с заголовком файла и телом фрагмента; при пустой выдаче или исключении возвращаются заранее заданные русскоязычные сообщения об отсутствии данных или об ошибке поиска.

Лексическая оценка в функции advanced_keyword_check (app/agent/grader.py) применяется как быстрый фильтр «очевидной нерелевантности» извлечённого текста к вопросу. Токены извлекаются шаблоном _TOKEN_PATTERN как последовательности кириллицы, латиницы и цифр длиной не менее двух символов в границах слова; далее для каждого токена вычисляется нормальная словоформа с помощью морфологического анализатора pymorphy3.MorphAnalyzer (экземпляр анализатора создаётся один раз и кэшируется декоратором lru_cache). Для вопроса и контекста формируются два множества лемм.

Первое правило отбраковки касается чисел: из вопроса и контекста извлекаются целочисленные литералы шаблоном _NUMBER_PATTERN; если в вопросе присутствуют числа, а в контексте не встречается ни одно из этих значений, контекст признаётся нерелевантным с фиксированной причиной «числовое несовпадение». Второе правило использует небольшой словарь предметных (учебных) лемм в константе _EDUCATION_TERMS: лабораторный, работа, задание, курс, тема. Если хотя бы одна из этих лемм присутствует во множестве лемм вопроса и одновременно ни одна из них не присутствует во множестве лемм контекста, контекст отбраковывается с причиной «нет учебной лексики». Если специальные правила не сработали, из лемм вопроса формируется список «ключей» — лемм длиной строго больше трёх символов, не являющихся чисто числовыми; доля совпадений ключей с множеством лемм контекста вычисляется как отношение числа совпадений к числу ключей (при отсутствии ключей в знаменателе в коде принимается значение 1,0). Порог принятия задаётся константой _RELEVANCE_THRESHOLD, равной 0,30: при меньшем значении доли контекст считается нерелевантным.

Если узел grader устанавливает is_relevant в отрицательное состояние, граф переходит к цепочке rewrite → search: запрос переформулируется как поисковая строка и выполняется веб‑извлечение; узел генерации синтеза ответа при этом исключает из набора сообщений для модели блоки локального контекста с префиксом RAG_CONTEXT_PREFIX, чтобы финальный текст не опирался на отбракованный локальный текст и использовал добавленную сетевую выдержку. Отдельно отмечается политика узла grader, при которой успешное извлечение реальных индексированных фрагментов (признак _rag_payload_has_hits) отключает лексический фильтр и предотвращает ложный уход во веб‑ветку там, где в сообщении уже присутствуют фактические строки базы документов.

2.5. Интеграция внешних информационных сервисов и вычислительных средств
В архитектуре рассматриваемой системы вызов внешней функциональности не оформлен как единый универсальный протокол удалённого «инструмента» на уровне одного формата сообщений; тем не менее семантически он реализует тот же класс задач, что и механика tool use: узлы графа агента переводят текст пользовательской реплики в параметры процедуры извлечения данных и фиксируют результат в сообщениях истории, после чего синтезируется ответ. Для погодных сведений и энциклопедической выдержки применяются обращения к соответствующим HTTP‑сервисам; для веб‑поиска — обёртка поисковой выдачи через DuckDuckGo; для калькулятора — детерминированное вычисление выражения. Ниже основной акцент переносится на подсистему поиска объектов видеохостинга, как наиболее ярко выраженный пример каскадирования провайдеров и защиты от повреждённого запросного текста.

Экспортная функция search_youtube_videos модуля app/tools/youtube_tool.py выполняет последовательность нормализации запроса, построения набора поисковых вариантов и итерацию по стратегиям доступа к источникам. На этапе нормализации применяется _strip_tool_query_noise: если текст запроса имеет вид строкового представления списка или словаря с полями типа type и text, выполняется попытка разбора литералом ast.literal_eval с извлечением конкатенации полей text. Данная санитизация устраняет ситуацию, когда ответ языковой модели в маршрутизаторе транслируется в поисковый запрос как repr составных блоков (в т.ч. мультимодальной структуры), что без преобразования приводит к некорректным обращениям к HTTP API и деградирует качество поиска.

Далее функция _search_query_variants формирует до десяти альтернативных формулировок базового запроса: для «технических» запросов добавляются суффиксы вида «tutorial», «course» и специальные комбинации при наличии терминов экосистемы LangGraph/LangChain; для запросов класса развлекательного характера (по регулярному шаблону _CASUAL_HINT) избегается навязчивое добавление учебных ключей и вводятся альтернативы с «видео», «youtube», англоязычными синонимами и сборниками. Таким образом компенсируется различие между «курсовой» и «развлекательной» семантикой при выдаче.

Каскад провайдеров собирается списком стратегий. При наличии ключа youtube_data_api_key в настройках в начало добавляется функция youtube_official_api, вызывающая search_videos модуля app/tools/youtube_data_api.py. Реализация выполняет HTTPS‑запрос к конечной точке поиска YouTube Data API v3 (search.list, часть snippet, тип video), с ограничением maxResults, параметрами регионального кода и языка релевантности, фильтрацией идентификатора из ответа и формированием «стабильной» ссылки watch?v= на конкретное видео. При сетевых сбоях, неуспешном HTTP‑коде или невалидном JSON модуль возвращает пустую выдачу без выброса исключения наверх, что позволяет перейти к следующей стратегии.

Порядок остальных методов определяется флагом первичного провайдера youtube_primary_provider. При значении youtube после официального API (если ключ задан) применяются библиотека youtubesearchpython (VideosSearch) и два уровня DuckDuckGo‑поиска через DDGS.text с паттернами site:youtube.com (узкий режим broad=False и расширенный broad=True с дополнительными шаблонами, в т.ч. для кириллических формулировок). При альтернативной настройке первичного провайдера порядок местами меняется: сначала узкие DuckDuckGo‑стратегии, затем библиотека, затем широкая выдача.

Для каждой пары «вариант запроса × стратегия» вызов выполняется внутри call_with_retry с параметрами числа попыток и задержки из глобальных настроек HTTP; при получении непустого текстового результата каскад прекращается. Результаты DuckDuckGo фильтруются функцией is_valid_youtube_video_url: принимаются только URL конкретного ролика (watch?v=, youtu.be/<id>, shorts/<id>), отсекаются страницы без идентификатора видео.

При ошибках типа «несовместимость параметра proxies при обновлении httpx» библиотека VideosSearch пропускается возвратом пустого результата; при исчерпании стратегий пользователю возвращается русскоязычное сообщение о неудаче с рекомендациями переформулировать запрос и проверить ключ квоты при использовании YouTube Data API.

2.6. Приём загрузки пользовательских документов и подготовка текста индексирования
Приём файлов выполняется HTTP‑методом POST на маршрут /upload, объявленный в модуле app/api/routes/upload.py. Маршрутизатор включает зависимость require_api_key, поэтому при активированной в окружении политике секрета запросы без корректного заголовка ключа отклоняются на уровне фреймворка. Тело запроса имеет тип multipart/form-data с единственным полем файла UploadFile, передаваемым как обязательный параметр File(...).

Имя файла нормализуется функцией _safe_stored_name: извлекается последний сегмент пути, пробельные символы заменяются подчёркиваниями, длина имени ограничивается, запрещены токены вида «.» и «..», расширение приводится к нижнему регистру и проверяется на вхождение в список allowed_upload_extensions настроек приложения. По умолчанию допускаются расширения .pdf, .txt, .md, а также графические форматы .png, .jpg, .jpeg, .webp (перечень может быть расширен конфигурацией окружения). При несоответствии расширения возвращается код 400 с перечислением допустимых значений.

Файл записывается в каталог upload_dir из настроек с предварительным созданием каталога. Чтение входного потока выполняется блоками по 512 КиБ; накопленный размер контролируется относительно upload_max_bytes, при превышении запись прерывается с кодом 413, а частично созданный файл удаляется. После успешного сохранения индексирование запускается через run_in_threadpool(rag_service.process_file, path) во избежание блокировки цикла обработки асинхронных запросов тяжёлыми операциями ввода‑вывода и CPU.

В RAGService.process_file выбор загрузчика зависит от суффикса имени: PDF обрабатывается PyPDFLoader, изображения из множества _IMAGE_SUFFIXES — специализированным классом _ImageOCRLoader, прочие текстовые форматы — TextLoader с кодировкой UTF‑8. Для изображений OCR реализован вызовом pytesseract.image_to_string после открытия растра библиотекой Pillow; языковой пакет распознавания задаётся строкой rus+eng. При отсутствии зависимостей или ошибке распознавания формируется документ с пустым или служебным текстом, что приводит к предсказуемому, но ограниченному содержанию индекса. Распознанный текст подвергается обрезке пробелов; при полном отсутствии содержимого подставляется маркер «изображение без распознаваемого текста». Далее документ разбивается на чанки и добавляется в векторное хранилище с метаданными имени и канонического пути, а HTTP‑ответ маршрута загрузки возвращает поле status с текстовым результатом операции индексирования.
