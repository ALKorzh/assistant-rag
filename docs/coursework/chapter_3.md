3.1. Контейнеризация многокомпонентной системы и проксирование клиентского доступа
Развёртывание стека описывается файлом docker-compose.yml как набор изолированных сервисов с явными зависимостями готовности и фиксированным пробросом сетевых портов на хост.

Сервис qdrant использует образ официального хранилища, публикует порты HTTP и вспомогательного интерфейса 6333:6333 и 6334:6334, монтирует именованный том qdrant_data в каталог хранения данных контейнера и задаёт периодический healthcheck проверкой доступности TCP‑порта 6333 изнутри контейнера. Сервис ollama публикует порт 11434:11434, сохраняет артефакты моделей на именованном томе ollama_data и проверяется командой ollama list. Сервис ollama_init запускается на том же базовом образе, ожидает состояние service_healthy у ollama, выполняет однократную команду загрузки модели эмбеддингов через ollama pull с подстановкой переменной OLLAMA_EMBEDDING_MODEL (значение по умолчанию в команде — nomic-embed-text), адресуясь к демону по OLLAMA_HOST=http://ollama:11434, после чего завершается без перезапуска (restart: "no").

Сервис backend собирается из репозитория по Dockerfile в корне, подключает переменные окружения из файла .env, принудительно переопределяет внутриконтейнерные URL зависимостей QDRANT_URL=http://qdrant:6333 и OLLAMA_BASE_URL=http://ollama:11434, задаёт привязку приложения 0.0.0.0:8000, устанавливает путь приёма загрузок /app/data/raw и публикует 8000:8000. Условием старта является здоровье qdrant, здоровье ollama и успешное завершение ollama_init (service_completed_successfully), что исключает работу бэкенда до появления нужной модели в локальном сервисе эмбеддингов. Каталог ./data на хосте монтируется в /app/data для сохранения загружаемых файлов вне слоя образа.

Сервис frontend собирается из подкаталога frontend/ и публикует 5173:80, то есть внешнему клиенту доступен порт 5173, внутри контейнера статика обслуживается на 80‑м порту средой Nginx после стадии сборки Node. Зависимость depends_on: backend задаёт порядок подъёма без ожидания готовности HTTP, однако в сумме с ограничениями бэкенда обеспечивается согласованный запуск вычислительных зависимостей.

Сборочный файл Dockerfile бэкенда базируется на python:3.12-slim, устанавливает через apt-get пакеты сборки и системные зависимости оптического распознавания tesseract-ocr, tesseract-ocr-eng, tesseract-ocr-rus, затем инсталлирует Python‑зависимости из requirements.txt и запускает приложение командой Uvicorn на app.main:app с прослушиванием всех интерфейсов и порта 8000. Указание пакетов Tesseract в образе обусловлено индексированием графических загрузок средствами OCR в серверном конвейере.

3.2. Обеспечение надёжности и трассируемости HTTP API
Идентификатор запроса реализован классом RequestIDMiddleware (app/middleware/request_id.py) на базе BaseHTTPMiddleware. При поступлении HTTP‑запроса извлекается заголовок X-Request-ID; при его отсутствии генерируется новый идентификатор формата UUID4. Значение записывается в request.state.request_id для использования обработчиками и журналированием (logger.debug содержит связку идентификатора, метода и пути). После вызова следующего обработчика цепочки тот же идентификатор записывается в заголовок ответа X-Request-ID. В create_app конфигурация CORS включает явное раскрытие заголовка X-Request-ID клиенту через expose_headers, что позволяет читать идентификатор из браузерного окружения при кросс-доменном обмене.

Защита доступа к ресурсам диалога и загрузки задаётся зависимостью require_api_key (app/api/security.py): при непустом значении секрета api_key в настройках сравнение выполняется через secrets.compare_digest по байтовому представлению предоставленного заголовка X-API-Key и ожидаемого ключа; при отсутствии или несовпадении возвращается ответ с кодом 401. При незаданном секрете функция завершается без проверки (политика локальной разработки). Маршруты /health и /ready объявлены на уровне фабрики приложения в app/main.py и не подключают указанную зависимость ключом, что отделяет системные проверки от бизнес‑эндпоинтов, на которые ключ распространяется через маршрутизатор API.

Проверка «живучести» (GET /health) возвращает JSON {"status":"ok"} и характеризует факт работы процесса ASGI‑приложения без обращения к внешним сервисам. Проверка готовности (GET /ready) вызывает функцию check_readiness() (app/services/readiness.py), формирующую структуру с полем ready и вложенным словарём checks по компонентам qdrant и ollama, каждый с признаком ok и текстовым полем detail.

Для Qdrant клиент QdrantClient создаётся с заданным из настроек базовым URL и тай‑аутом пять секунд; проверка выполняется вызовом get_collections(). Любое исключение приводит к ok=false и записи текста ошибки в detail.

Для Ollama выполняется HTTP‑запрос методом GET к эндпоинту {ollama_base_url}/api/tags с тай‑аутом пять секунд. Успех означает код 200 и наличие набора имён моделей в ответе; далее выполняется проверка, что в множестве имён присутствует модель из настройки ollama_embedding_model, либо вариант с суффиксом :latest, либо любая строка имени, содержащая заданное имя (логика допускает различия именования в списке локального демона). При недоступности сервиса, неуспешном коде или отсутствии требуемой модели признак ok для Ollama ложен, а текст detail содержит пояснение (в т.ч. «модель не загружена»).

Фабрика приложения упаковывает результат в JSONResponse, выставляя код 200 при ready=true и код 503 при ready=false. Таким образом, эндпоинт готовности отражает не только исполнимость кода, но и достижимость векторной базы и готовность сервиса эмбеддингов к работе конвейера RAG, что соответствует разграничению liveness/readiness в эксплуатационных сценариях маршрутизации трафика.

3.3. Тестирование и непрерывная интеграция программной системы
Автоматизированная верификация поведения приложения организована на базе фреймворка pytest (python -m pytest, в т.ч. режим -q для сжатого отчёта). Тесты выполняются как регрессионный контур при изменении модулей сервиса: фиксация ожидаемых контрактов функций, ограничений обработки ошибок и инвариантов вспомогательной логики снижает риск регрессий при доработках графа агента и подсистемы извлечения.

Непрерывная интеграция для репозитория задана workflow GitHub Actions с именем CI (.github/workflows/ci.yml). Событиями запуска являются отправка изменений и открытие/обновление запросов на слияние в ветки main и master. Выполняется job test на среде ubuntu-latest с матрицей интерпретатора Python 3.12; последовательность шагов включает получение исходных текстов (actions/checkout@v4), установку Python с кэшированием каталога pip (actions/setup-python@v5), установку зависимостей из requirements.txt и запуск python -m pytest -q. На уровне описанного файла отдельный этап статического анализа (линтинга) явно не включён; расширение пайплайна дополнительными проверками качества кода остаётся инженерным вариантом развития процесса, не противоречащим базовой схеме «установка окружения → тестовый прогон».

Приёмочная оценка функциональности агента дополняет автоматический контур сценарными проверками, недетерминированными по полному покрытию из-за зависимости от внешних LLM‑сервисов. Практический протокол включает прогон пользовательских формулировок с фиксацией фактической ветви графа по журналам (например, выбор узла маршрутизации, переход rag → grader, ветвление is_relevant к generator либо цепочке rewrite → search) и сопоставление результата ожидаемому сценарию. Для фильтра контекста дополнительно проверяются случаи семантического извлечения с заведомо слабым лексическим пересечением: ожидается срабатывание эвристик advanced_keyword_check и переход к веб‑поиску с исключением блока локального контекста из промпта генератора. Для сценария с наличием индексированных фрагментов в тексте ответа RAG допускается обход лексического запирания согласно логике узла grader, что также подлежит фиксации в приёмочном перечне.

Заключение
В ходе выполнения курсовой работы сформулирована и достигнута цель разработки программного комплекса диалогового ИИ‑ассистента, сочетающего семантическое извлечение по локальной документальной базе, маршрутизацию запросов к набору информационных сервисов и поставку интерфейса взаимодействия пользователя в составе контейнеризуемой архитектуры. Поставленные задачи решены: выполнен теоретический обзор ограничений генеративных моделей и технологии Retrieval‑Augmented Generation, описана целевая архитектура клиент‑серверного взаимодействия, раскрыты решения по графу управления состоянием, по конвейеру индексирования и лексической фильтрации контекста, по интеграции внешних API и по развёртыванию с разграничением проверок живучести и готовности HTTP‑сервиса.

Основными техническими результатами являются: реализация управляемого агента на базе LangGraph с явной топологией переходов между узлами маршрутизации, извлечения и генерации; настройка пайплайна RAG с записью векторов в Qdrant и получением эмбеддингов через локальный сервис Ollama; введение морфологически и лексически обусловленного грейдера релевантности локального контекста с резервной веткой веб‑извлечения; интеграция энциклопедических, погодных, вычислительных и поисковых сценариев, включая каскадируемое обращение к провайдерам YouTube и защиту поискового запроса от искажений формата ответа LLM; конфигурирование эксплуатационного контура (промежуточное ПО трассировки X-Request-ID, опциональная проверка ключа, эндпоинты /health и /ready, Docker Compose с сохранением состояния томов и сборка бэкенда с зависимостями OCR).

Практическая значимость работы заключается в воспроизводимом шаблоне «локальные данные + управляемые ветвления + наблюдаемость API», применимом в учебной и исследовательской среде. Направления дальнейшего развития включают расширение набора инструментов и политик качества извлечения, ужесточение оценочных метрик RAG, подключение голосового ввода и синтеза речи как дополнительных каналов клиента, усиление набора автоматических проверок (статический анализ, интеграционные тесты против поднятого стека), а также эксперименты с альтернативными эмбеддинг‑моделями и схемами ранжирования без снижения требований к согласованности размерности вектора и метрики индекса.
