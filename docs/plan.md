# Содержание курсовой работы на тему: «Разработка интеллектуального ИИ-ассистента на базе агентной архитектуры и технологии RAG»

## Введение

Актуальность исследования (роль больших языковых моделей, ограничения «голого» LLM без внешних данных и проблемы достоверности ответов; значение технологии RAG и оркестрации многоинструментальных сценариев для прикладных ассистентов).

Цель работы — разработка и описание программной системы персонального ИИ-ассистента на основе пайплайна RAG по локальным документам, агентной маршрутизации запросов к специализированным инструментам и клиент-серверного взаимодействия с веб-интерфейсом и контейнеризованным окружением.

Задачи исследования:
- выполнить анализ ключевых подходов (LLM, RAG, векторный поиск, агентные графы);
- описать архитектуру разработанного решения (бэкенд, фронтенд, зависимые сервисы);
- рассмотреть проектирование графа состояний и маршрутизацию сценариев;
- рассмотреть реализацию извлечения и генерации при RAG и механизм лексической оценки релевантности контекста;
- охарактеризовать интеграцию внешних информационных сервисов;
- описать развёртывание, наблюдаемость готовности и тестирование.

Объект исследования — программная система интеллектуального ассистента с возможностью обработки текстовых запросов пользователя при участии набора средств информационного поиска и синтеза ответа.

Предмет исследования — методы и программная реализация агентной оркестрации запросов, семантического поиска по документальной базе (RAG) и средств надёжного функционирования HTTP API при контейнеризованном развёртывании.

Положения, выносимые на защиту (краткий перечень ключевых результатов: архитектурная схема, описание узлов LangGraph и ветвлений, описание пайплайна RAG и grader-фильтра, интеграции, Docker/Nginx и проверки готовности).

## ГЛАВА 1. ТЕОРЕТИЧЕСКИЕ ОСНОВЫ И ОБЗОР ПРЕДМЕТНОЙ ОБЛАСТИ

### 1.1. Интеллектуальные ассистенты и большие языковые модели: ограничения и требования к прикладным системам  
Роль генеративных моделей как ядра диалогового ассистента; необходимость подключения внешних источников и инструментов для фактологичности и специализированных операций.

### 1.2. Технология Retrieval-Augmented Generation (RAG): концепция, этапы и типовая архитектура  
Разделение на индексацию документов, извлечение релевантных фрагментов (чанков), формирование контекста и генерацию ответа; связь параметров разбиения текста (`chunk size`, overlap) с качеством извлечения.

### 1.3. Векторные базы данных и семантический поиск по эмбеддингам  
Представление документов в виде многомерных векторов; модель семантической близости (косинусная метрика в описываемом решении); роль локального провайдера эмбеддингов (Ollama) и соответствия размерности вектора параметрам коллекции (Qdrant).

### 1.4. Агентные подходы к оркестрации LLM и графы состояний  
Идея маршрутизации запроса к различным действиям; преимущества явного описания переходов и узлов как основы наблюдаемости и воспроизводимости сценариев; связь понятий «роутинг», «инструменты», «ветвление» с практической реализацией на LangGraph.

## ГЛАВА 2. ПРОЕКТИРОВАНИЕ И РЕАЛИЗАЦИЯ ИНФОРМАЦИОННО-ПОИСКОВОГО И ДИАЛОГОВОГО КОМПЛЕКСА

### 2.1. Обоснованный выбор стека технологий для реализации ассистента  
Сводная характеристика слоя бэкенда (Python 3.12, FastAPI, Uvicorn, Pydantic), оркестрации (LangGraph, LangChain-связки), модели Gemini (/langchain-google-genai), клиент-серверного UI (React, TypeScript, Vite, Tailwind), а также смежных библиотек (OCR, морфология) в контексте заявленных функциональных возможностей.

### 2.2. Архитектура клиент-серверного взаимодействия и проксирующие элементы конфигурации  
Схема «браузер → HTTP API FastAPI»: эндпоинты диалога и загрузки документов; роль статического раздавания интерфейса и прокси `/api/*` через nginx в Docker; отличение локальной конфигурации разработки (прокси Vite) от контейнерного развёртывания.

### 2.3. Модель состояния и граф управления диалогом на базе LangGraph  
Описание набора узлов (`router`, `rag`, `grader`, `rewrite`, `search`, узлы специализированных инструментов, `generator`, `reflection`) и логики переходов: ветки RAG при релевантном/нерелевантном контексте, переход из нерелевантного контекста в веб-поиск после переформулирования запроса, пост-генерационная проверка с возможным повтором ответа; различение режимов вызова LLM (маршрутизатор при низкой температуре и генератор ответа при иных параметрах безопасности и температуры).

### 2.4. Пайплайн RAG для локальных документов и морфологически основанная оценка релевантности извлекаемого контекста  
Разбиение документов на фрагменты, параметры ограничения выдачи из вектора хранилища, механизм «подсказок из вопроса» для упорядочивания результатов извлечения; описание lexical grader на основе pymorphy3 (лемматизация, числовые признаки, предметный лексический словарь учебной тематики) и переход к веб-поиску при отбраковке контекста.

### 2.5. Интеграция внешних информационных и вычислительных средств как расширяемых узлов системы  
Погода через OpenWeather, Wikipedia через MediaWiki-совместимый доступ, калькулятор как детерминированное вычисление выражений, веб-поиск через DuckDuckGo после переписывания запроса; особенности поисковой выдачи YouTube (очередность источников: YouTube Data API v3 при наличии ключа и деградация альтернативными провайдерами, эвристики типа запроса, санитизация текста перед поиском при мультимодальных выходных форматах Gemini).

### 2.6. Приём загрузки документов и подготовка данных для индексации  
Поддерживаемые форматы (PDF/текст/Markdown/изображения), использование OCR (Tesseract rus+eng в образе), ограничения по размеру и расширениям, размещение файлов данных в томе `./data`.

## ГЛАВА 3. РАЗВЁРТЫВАНИЕ, НАБЛЮДАЕМОСТЬ ГОТОВНОСТИ И ПРОВЕРКА КАЧЕСТВА

### 3.1. Контейнеризация многокомпонентной системы и обратное проксирование веб-доступа  
Сервисная модель Docker Compose (Qdrant, Ollama, инициализация загрузки эмбеддинг-модели, бэкенд, интерфейс на nginx/Vite-бандле); сопоставление портов и именованные тома для сохранности данных БД и моделей; процедура сборки образа бэкенда и системных зависимостей (Tesseract).

### 3.2. Обеспечение надёжности и трассируемости HTTP API: middleware, ключ доступа и проверки жизненного цикла  
Промежуточное ПО назначения/проброса `X-Request-ID` и включение корреляции в логи; условное требование `X-API-Key` через сравнение с секретом из конфигурации; различие «жизнеспособности процесса» (`GET /health`) и «готовности зависимостей» (`GET /ready` с проверкой Qdrant и наличием модели эмбеддингов в Ollama, включая код ошибки при неготовности).

### 3.3. Тестирование и непрерывная интеграция программной системы  
Организация автоматических модульных тестов (pytest) и конфигурация GitHub Actions на pull request для проверки установки зависимостей и успешности тестового прогона; приём оценочного тестирования сценариев (соответствие веток графу, качество фильтрации контекста, корректность интеграций по описанному протоколу API).
